# 控制流与副作用

- **控制流集中，具体操作拆小。** 一个业务动作的分支、顺序和状态转换应能在同一处顺着读完。
- 不要为了缩短函数，把判断、重试、错误分支逐层藏进 helper。抽出的函数负责具体操作，例如读文件、编码请求、写入状态，而不是接管半段业务流程。
- 长函数先减少重复工作、重复状态和无意义分支，再决定操作边界。不能靠机械拆函数达成行数要求。
- 优先用 `match` 表达互斥状态和完整分支。不要堆叠 `matches!`、否定条件和 early return，把一次转换写成一串门禁。
- 减少嵌套。遇到多层缩进，先重建状态模型、合并互斥分支、去掉重复判断；不能将七层嵌套原样搬到多个 helper。
- 副作用留在明确的操作边界，业务编排保留在中心流程。

# 类型：Parse, don't validate

- 外部字节、字符串、JSON 在边界解析成有语义的类型。内部函数接收已经解析的信息，不重新校验。
- 完成一次检查后，返回类型必须体现取得的事实。不要写 `Response -> Result<Response>` 这样的“检查成功再返回原对象”接口。
- 用 sum type 表达互斥状态。**自有函数参数不传布尔值**；检查布尔是否与另一个参数共同组成一个枚举，例如 `Option<T> + bool` 应改成带 payload 的枚举。
- 不用多个 `Option` 和布尔拼出非法状态组合。只有值确实可以缺失时才使用 `Option`。
- 外部协议要求的布尔值在序列化/解析边界转换；不要因此把同一布尔表示一路传进内部状态。第三方 trait 固定的签名在实现边界接入内部模型。
- 动作负责完成状态转换。例如 enroll 按请求建立或替换身份，不因为旧状态属于另一个 origin 就额外拒绝转换。
- 库和业务逻辑不靠 `unwrap`、`expect` 或任意 `unsafe` 驱动正常流程。测试与调用入口可以使用 `unwrap`、`expect`；不要将入口和库混为一谈。
- 必要的 unsafe 限定在维护不变量的实现边界，说明具体安全前提。不要配置整个 workspace 的 `unsafe_code = "forbid"`。

# 内存、表示与访问方式

- 自有实现中**不使用 `Vec<T>` 或 `Box<[T]>`**。成组记录必须采用 **SoA**。
- 减少 pointer indirection。避免逐元素 `Box`、树状堆对象和只为包装而存在的指针层。能内联的字段内联；变长数据用集中存储与偏移引用。
- 以不分配为实现目标，不只优化热路径。循环复用缓冲区；不要为遍历临时 collect，不要为了调用 helper 克隆记录，不要对同一输入反复 parse/serialize。
- clippy的 large enum variant 不能 Box enum variant 修复。忽略，如有集合需求，写成 SoA。

# 命名与字面量

- 遵守 naming skill：通常一个词，最多两个词。使用惯用缩写；不要把多个词挤成一个词来绕过限制。每个修饰词都必须在当前上下文中承担区分作用。
- 身份类型直接叫对应的事物，例如 `Device`；不要加 `Id` 后缀。字段也不要因其存储了身份就机械叫 `device_id`。
- 即使只有两个词，也要检查是否重复。例如只有一种目录时，不再加没有区分作用的前缀。
- **路径规则按稳定版 Rust 能否通过 `use` 独立导入目标项划分。** 模块中的自由函数、类型、模块级常量和 enum variant 先导入，再使用短名；有冲突时用明确的导入别名，不保留冗长限定路径。
- 不能通过 `use` 独立导入的关联项允许 `::`：inherent / trait 关联函数、方法、关联常量、关联类型，包括 `Self::Err`、`D::Error`、`R::Refs<'a>`。自有 API 与第三方 API 使用同一规则，不再要求改成接收者调用。
- 不为消除这些允许的路径增添泛型参数、具体类型展开、转换、包装函数、marker receiver 或改写 GAT。此前仅为消除路径所做的替代应恢复直接表达。
- `use` 声明和宏路径允许 `::`。规则的语义边界、正反例和未来 lint 判定顺序见 [路径规范](references/paths.md)。
- 直接使用关联常量，例如 `JsValue::NULL`、`StatusCode::GONE` 和类型化服务标志；不要仅为避免 `::` 改成函数调用、裸数字或底层常量加转换。
- 保留惯用的 `Arc::clone(&value)`，显式表明克隆的是共享所有权、增加引用计数；不要为了改成接收者调用而替换成 `value.clone()`。这是明确允许的 trait 关联调用写法。
- **禁止所有 turbofish：`::<T>`、`::<T, U>`、`::<_>` 等全部删除，包括 inherent method 上的泛型实参。** 推导不足时在 `let` 绑定上标注类型，将链式表达式拆成有类型的中间结果；不要换个 helper 继续写 turbofish。

```rust
let value: Settings = from_str(input)?;
let address: IpAddr = host.parse()?;
```

- 上述规则同样适用于测试、新增文件和宏定义中的自有代码；不能只清理当前看到的几个调用点。
- 字符串字面量不要散落在控制流中。协议值用枚举/类型；SQL、模板和较长文本放到有语义的独立操作或资源中；共享的文本集中定义。
- 不要为一个只用一次且已经清楚的值发明超长常量名。目标是让业务控制流清楚，不是机械搬动字面量。

# 模块与视觉布局

- 自有代码文件不超过 200 行。按概念和具体操作拆模块，不按行号切割业务编排。
- `lib.rs` 只负责连接私有模块与 re-export，不放函数、类型或实现。不用 `pub mod` 把内部目录结构直接当作公共 API；通过 `pub use` 暴露所需项。
- 有子模块的目录使用 `mod.rs` 作为入口。目录入口也保持薄，不把业务实现搬进 `mod.rs`。
- **先集中写所有 `mod`，再集中写所有 `use` / re-export**，不要 mod/use 交替排列。
- 函数、类型声明、`impl` block 等顶层 item 之间必须有空行。用户说的顶层 item 不是要求每条 `use` 之间都加空行。
- 不在函数词法域中声明 `struct`、`enum`、`impl` 或具名函数。放到模块顶层；正常的闭包不等于具名嵌套函数。
- 所有代码运行项目 formatter。formatter 不处理的逻辑段落与空行也要人工整理。不要写成挤在一起的大块代码。

# 宏

- 主动、大量使用宏承载真正重复的结构：语义 newtype、枚举的 wire 映射、列存储访问、重复序列化和固定结构声明。
- 同一种结构反复出现时，先找已有宏；扩展已有宏优先于复制实现。
- 宏体现共同规则，调用点保留差异。不要用宏隐藏业务分支、状态转换和副作用顺序。
- 不为满足“使用宏”而给单次操作加一层宏，也不另造一门难读的 DSL。
- 宏展开的项目类型、字段和方法同样需要文档与合适的可见性。

# 文档、lint 与日志

- 公共项和 private item 都写 Rustdoc，解释语义、边界和不变量，不只把名字翻译成一句话。
- 压缩表示需要注明其语义上的朴素 ADT，以及字段/位/列怎样对应它。
- 两个 lint 都在 workspace 集中启用，由 crate 继承：

```toml
[workspace.lints.rust]
missing_docs = "warn"

[workspace.lints.clippy]
missing_docs_in_private_items = "warn"
```

各 crate 的 `Cargo.toml` 使用已有的继承配置；缺少时添加：

```toml
[lints]
workspace = true
```

- 不启用整个 workspace 的 `unwrap_used`、`expect_used`，不设置 `unsafe_code = "forbid"`。这不是允许库代码随便 unwrap，而是作用域与使用位置要分清。
- 不在各文件顶部重复添加 `#![warn(...)]`、`#![deny(...)]`；不靠 blanket allow 隐藏自有代码的问题。
- 程序运行日志使用 `tracing`，不使用 `print!` / `println!` / `eprintln!` 输出运行状态。机器协议输出使用对应 serializer/writer。
- ANSI 颜色控制码在产生日志或后端接收边界处理。前端不要 strip，不要承担后端的解析和清洗职责。
- 前端展示后端模型，保留服务端具体错误。不要换成丢失原因的笼统提示，也不要附加用户没要求的解释性小字。

# 功能边界与可用性

- 不添加用户没要求的鉴权、validator、probe、发布门禁或前置检查。开发测试不能变成产品使用时的新门槛。
- 不能因为观察或辅助功能失败，就阻止配置发布、安装或状态转换。错误记录具体原因，作用范围与失败的操作一致。
- 安装参数和使用方式从已经确定的安装流程推导，不额外设计无人使用的交互路径。
- 安装和脚本能够重放；覆盖实际中断和失败现场。修复落在项目中，不靠一次手工操作才让产品可用。
- 用户指定 fresh install 时就按 fresh install 实现，不顺手加入旧格式迁移、旧文件删除、兼容分支。
- 不擅自加文件类型、非 symlink、任意长度限制等额外限制。
- 一个对象有创建入口，就要考虑重命名、删除和关联资源释放。不能创建以后留下无法管理的资源。
- 前端不使用 `h1`、`h2`。布局紧凑，遵守用户已有的 dashboard 规范。

# 完成修改

先在真实调用链上完成实现，再检查上述表示、控制流与命名是否贯穿全程。测试应复现用户遇到的故障，验证实际结果；安装与运行问题要在用户指定的平台、服务器或隔离实例中执行，不能只靠编译通过交付。

提交保持小而完整，删除废弃实现和调用路径。使用已有本地工具链、依赖和构建缓存；不要为每次提交重复消耗远端多平台测试资源。按用户要求发布，不擅自改部署授权或引入新的审批步骤。
